# Komari 集成体验与功能归属审计

日期：2026-10-21
基线：ShellBeam `bfe6b674982fea524fb6f2b4d5b724a66abd07c2`，PRD 0.4
性质：产品与实现分析。事实基线仍为上述提交；产品方向已按用户决策调整为 PRD 0.5，下文问题判断保留该基线。首批修复和共享资料同步的实施状态独立记录在验收矩阵，不将整份分析视为已经解决。

## 1. 结论与对上一轮判断的修正

当前已经改善了默认列表密度、可选展示和窗口切换，但尚未完成产品职责的统一。把 Komari 全站移入主窗口，仍会让用户进入另一套主机、终端、任务、通知和设置。此前“两个核心目标基本达成”的结论只适用于日常入口与容器变化，不能扩展为“集成体验已经足够清晰”。

这不是单纯的布局问题。根因是：同一台服务器对应不同管理对象，同名动作写入不同系统，观察状态与人工处理状态混在一起，且部分入口没有表达这种区别。CI 通过证明既有断言成立，并不能证明产品语义正确。本次发现并隔离复现了一处规则数量被解释为故障的错误。

已确定方向：ShellBeam 提供完整的原生客户端，Komari 是可选后端。用户使用一份主机目录、一套设置与一个保存入口；共享业务字段的双向同步、任务编排、部分失败和冲突恢复由 ShellBeam 负责。不能要求用户理解两份存储或在两个后台完成同一操作。

技术上的身份、权限、采集证据和存储差异仍需准确建模，但不再成为两套产品体验。Komari 品牌只在后端接入、探针安装和高级诊断中按需出现。原站只能作为过渡调试入口，不能代替原生能力，也不能作为完整接管的验收路径。具体契约和开发阶段以 PRD 0.5 第 7 节、第 11 节为准。

对参考分析的取舍：采用其对对象、动作、告警语义和重复工作流的诊断，不采用“独立远端管理域”作为长期客户端方案。多个入口或模块数量本身不能证明体验失败；主机与 VPS 已有同源部分，不应称为多套独立数据。不同采样时间或来源的指标不一致也不自动构成缺陷。下文分别列出已复现错误、代码风险和待验证体验，避免把它们混为结论。

## 4. 已确认的问题，按优先级排序

### P0：规则数量被误当成正在发生的故障

官方 1.6.0 `GET /api/admin/notification/offline` 返回离线通知配置表。模型包含 `client`、`enable`、`grace_period`、`last_notified`，不包含可靠的当前 firing/resolved 状态。查询未过滤禁用规则。此版本未注册旧 `/notification/load/` 路由，但另一个 endpoint 成功仍会保留其数量。

现有处理链：

1. `komari.ts:367` 读取集合；数组长度成为 `offline`，无法得知活动状态时 `active=null`。
2. `komari-alerts.ts:286` 将配置数量转成告警 observation。
3. `komari-alerts.ts:402` 只依据 `count > 0` 创建 active 记录，不使用 `active`；offline 默认 critical。
4. 相同数量仍存在时，用户关闭的记录会在下次 reconciliation 重开。

本次两项隔离复现均证实：仅一条 `enable:false` 的配置会形成 active/critical 事件；即使输入明确 `active:0`，正数规则数量仍能生成 active 事件。测试通过表示成功复现缺陷，不是正确行为验收。

修订原则：规则数只能显示为配置统计。缺少活动事件证据时显示“当前事件状态不可用”，不能创建故障，也不能由规则删除推断恢复。即使服务端只给全局 active 总数，也不能擅自分配到每种规则或每台主机。需要稳定事件身份、对象、状态及时间才能形成远端事件；采集错误则明确作为 ShellBeam 观察到的数据源事件。修复应保留旧 ID/审计，标识旧记录缺少事件证据，不批量伪造“已恢复”或补发恢复通知。

### P0：统一告警入口仍让本地处理看起来像远端操作

`host-alerts-center.tsx` 的按钮都是“确认/关闭”；`komari-alert-actions.ts:139` 实际只更改 ShellBeam 本地生命周期。确认弹窗虽然说明远端不变，但用户在阅读列表和判断结果时仍容易误解。

需要两个独立维度：

- **异常状态**：数据源报告异常、正常，或当前未知。
- **处理状态**：ShellBeam 中未处理、已确认、已归档。

例如应能明确呈现“监控仍中断 · 已确认”。人工处置不能使健康变绿或伪造恢复；确认、静默、规则停用是不同业务动作。原生客户端应按后端能力完成所选动作需要的写入；需要远端更新却失败时不能报告全部完成。内部保留执行范围与证据，按钮、结果反馈和审计使用同一种语义，不让用户自己协调两套处置记录。

### P0：同窗原站保留第二套工作台，审计边界不清

`komari-administration-panel.tsx:40` 是全屏覆盖层，里面加载整站 WebView。它没有限定原站导航，ShellBeam 的日常上下文被暂时遮住。原站还有自己的终端、文件和远程执行；这些动作不会因嵌入网页就自动变成 ShellBeam OperationJob。

这不是已证实的权限漏洞，而是用户对执行方式、确认机制与审计归属的预期冲突。目标是由原生页面和后端适配器接管任务，统一确认与审计。原站只能作为明确标注的过渡调试入口；缺少稳定 API 的能力属于待解决的协议、兼容性或实现缺口，不能把跳转原站计作完成原生接管，也不能用 CSS 隐藏菜单假装已经统一。

### P1：主机、VPS 资产与监控节点的入口和对象尚未统一

ShellBeam `HostProfile` 实际是 SSH 连接配置，必需地址、端口、用户名、认证方式及相应的必要凭据；Komari 节点是监控对象，两者不是同一个数据库实体。ShellBeam 自身又把同一 hosts 集合放进主机页和 VPS 资产页，Workspace 里也有资产入口。

应先统一主机目录的展示与操作，再逐步完善“主机身份 + 可选 SSH 连接 + 外部节点关联”的能力模型。当前不能用没有密码的假 SSH 连接来模拟纯监控主机，也不能按 IP 相同就悄悄合并记录。同一机器可能有多个 SSH 账号、多个地址或多个监控来源。

资产页当前资源值直接来自旧 monitor/inventory 路径，而主机和 Workspace 已使用 Provider 选择规则。这证明读取路径不同，存在显示不同来源数值的风险；本次没有制造真实多来源分歧，不能声称已复现数值错误。下一轮必须统一投影并补充此场景。

### P1：设置分类尚未形成统一编辑与保存流程

“监控与通知”当前主要放通知；数据源在“集成”；采集重试和 Agent 发布在“高级”；主机规则在健康检查里；原站又有通知与系统设置。用户需要先理解实现方式才能找到配置。

解决方式是围绕主机、监控、通知、连接安全等用户任务提供一套原生设置和保存流程。设备范围、主机范围和账号权限等影响用户决策的信息仍需明确；具体写入哪份数据库由同步契约负责，不能要求用户据此选择第二个设置页。共享配置需要持久化、双向同步和失败恢复，不能仅以分类标签代替这些能力。

### P1：接入流程仍存在实质断点

- 当前流程要求原站先签发并保存 Key，ShellBeam 再保存连接凭据；Web 登录与 API 认证分离，当前实现不支持统一授权。该现状是原生接入需要解决的缺口，不是长期要求用户操作两边的理由。
- 关联面板只能选已有主机；空 Vault 只有“没有主机”，没有就地创建/导入/返回路径。
- 完成页没有直接进入已关联主机的闭环。
- 主机的数据源详情没有“管理此关联”的定向入口，需要自行返回设置寻找服务。
- “恢复自动匹配”删除手动绑定后，下一次仍可能按地址/名称关联；缺少明确的“不使用此节点/不再自动关联”状态。
- “移除”连接没有充分表达范围：本地连接配置删除不等于删除 Komari 服务器、卸载 Agent 或清除所有远端记录。

### P1：通知、探针和历史继续让用户承担实现差异

- ShellBeam 与 Komari 各自可以发送通知，目前没有跨产品投递去重保证。ShellBeam 的冷却与 eventId 去重不能阻止远端发送同一问题的提醒。
- “启用只读同步”说明的是 ShellBeam 的调用行为。本地官方版本中服务器 API Key 可以具有管理员身份，不能因此称其为只读权限的 Key。
- Komari Agent 与 ShellBeam Agent 是两种部署；当前 Link 模型把两者并列，健康 Komari 且没有 ShellBeam Agent 也可能推荐安装探针。可选替代来源不应被包装成修复 Komari 的必经步骤。
- 活动页把 OperationAudit 放进上方活动流后，又完整挂载 OperationsAuditCenter。同一操作的重复展示应改成摘要链接与同一详情，不删除底层记录。

## 5. 应保留的合理重用

- 主机列表显示 CPU 摘要、详情显示时间序列，是不同信息层级；共用数据投影、时间与语义即可，不必只保留一个入口。
- 全局 SFTP 用于选择连接，主机 Files 用于当前主机任务，可以保留入口并共用功能与状态。
- 告警中心和主机详情指向同一事件与处理状态；活动页和主机任务入口指向同一 OperationJob。
- “已知主机”是 SSH 信任指纹，不能与业务主机合并。应改称“SSH 信任记录”或增加明确说明。
- 服务器管理仍有价值，但属于 ShellBeam 原生高级设置的能力，不再提供另一套日常主机、任务和设置工作台。

判定标准是同一对象和同一操作能否连续完成、各入口结果是否一致，不是页面或菜单数量。底层存在多个写入目标时，由同一原生操作编排，不转交用户分别处理。

## 6. 统一对象与字段同步契约

下表是 PRD 0.5 新规划的摘要，尚未实现。内部字段归属用于保证正确写入，不是让用户选择在哪个产品编辑。

| 对象/字段 | 统一客户端行为 | 实现约束 |
| --- | --- | --- |
| 主机名称、分组、标签等共享资料 | 原生主机详情编辑一次；按适配器支持双向同步 | 定义字段映射、共同版本与冲突策略，不能用设备时间直接覆盖 |
| SSH 地址、用户、凭据、ProxyJump | 同一主机的连接设置负责管理 | SSH 目标与观测 IP 语义不同；不把 SSH 凭据上传给监控后端 |
| 节点 UUID、Agent 身份、注册 | 原生接入与探针流程管理 | 稳定绑定后端实例与节点身份；解绑、删除节点、卸载探针是不同动作 |
| CPU/内存/网络及样本时间 | 各视图共用一套指标投影 | 保留原始样本、采样时间和回退依据，不把旧值改成实时数据 |
| 资产价格、到期、地区等共享资料 | 同一资产详情保存并同步；外部修改可拉回 | 明确可编辑字段、单位和空值语义；不能让旧快照覆盖新编辑 |
| 规则、渠道及服务设置 | 原生监控与通知设置统一编辑、保存和验证 | 适配器提供真实读写能力；部分失败可恢复，不以本地保存冒充远端完成 |
| 告警事件与处置记录 | 统一事件、处理状态和操作详情 | 故障事实与人工处置分离；有真实远端操作能力才执行并验证对应更新 |
| 后端地址、授权与绑定 | 单一接入流程完成授权、持久化、认证和发现 | 不混用 Web session、服务器 API Key、Agent Token；凭据存 Vault 引用 |
| 桌面权限和客户端外观 | 原生应用设置管理 | 保留设备范围；不因服务器主题或渠道变化改变无关客户端设置 |
| OperationJob 与外部历史 | 原生操作统一审计，外部变更按证据关联 | 一次用户意图对应一个任务；保留真实来源，不能伪造外部任务的本地发起记录 |

主机实体使用稳定 hostId，可以有零或多个 SSH 连接与监控绑定。名称/IP 变化不改变主机身份，同 IP 不自动证明是同一主机。迁移保留现有 hostId、凭据引用、映射、快照和 OperationJob；纯监控主机不需要伪造 SSH 地址或凭据。

一个保存流程至少需要：持久化期望值与待同步任务、执行远端写入、读回确认、更新共同版本。只完成其中一部分时显示“同步中”或可处理的失败；远端已成功但响应丢失时先查询结果，不能盲目重复危险操作。重启恢复队列，Vault 锁定和绑定版本变化阻止旧任务误发。外部改动采用三方合并，不同字段自动合并，同字段冲突在原生界面解决；删除与排除意图不得被旧队列复活。完整契约见 [PRD 第 7 节](./prd-terminal-ops.md)。

## 7. 统一原生信息架构

日常导航使用 ShellBeam 的任务语言，Komari 是接入时可选择的后端类型：

```text
主机（同一份目录）
  连接视图〔默认〕 / 监控视图〔主动开启〕 / 资产视图
  某台主机
    概览、终端、文件、服务/进程、其他运维工具
    告警与操作记录〔同一事件/任务的上下文入口〕
    主机资料、连接设置、监控配置〔原生编辑与同步结果〕

告警中心〔按实际监控能力与事件渐进提供〕
  当前异常、处理与历史；统一确认、静默、规则入口
活动与任务
  连接活动、OperationJob、事件审计、待同步与冲突处理
工具
  保留原有 SFTP、端口转发、凭据与代码片段的效率
设置（一套原生设置、一个保存流程）
  应用：外观、终端、设备权限等
  连接与安全：SSH、信任记录、Vault
  监控与通知：后端接入、采集、探针、规则与历史
    渠道、发送策略、静默与投递结果
    监控服务 → 服务管理〔原生低频设置〕
  高级：MCP、签名制品发布与诊断
```

VPS 资产可成为主机页的视图，原入口保留连续跳转。“设备同步”“保管库备份”“SSH 信任记录”使用对象名称说明用途。未接入监控的用户保持原有连接体验，不展示无关错误占位、Agent 安装任务或 Komari 专属流程；通用 SSH 运维仍可主动使用。

品牌仅在后端选择、兼容探针安装与高级诊断中出现。接入、初始化、管理及故障处理应逐步由原生界面承接；过渡原站调试入口不得进入这些流程的完成条件，也不因嵌入主窗口而被认定为原生能力。

## 8. 一次操作的完成契约

| 用户动作 | 原生流程必须实现的结果 | 不得伪装的完成状态 |
| --- | --- | --- |
| 修改共享主机名称/分组 | 一次保存更新期望值并同步支持的关联目标；外部修改可同步回来 | 只改本地后声称各端已一致 |
| 修改 SSH 目标 | 更新同一主机的连接资料并核查关联可信度 | 把观测 IP 当 SSH 地址，或改写 Agent 身份 |
| 导入/关联监控节点 | 原地创建纯监控主机或绑定已有主机，完成后进入该主机 | 要求用户先手工创建假 SSH 连接 |
| 解除关联并不再自动关联 | 保存排除意图，后续同步、重启和旧队列不复活 | 只删除手动覆盖，再自动接回 |
| 编辑规则/通知/服务配置 | 原生保存统一编排所需读写、验证和任务记录；失败可原地恢复 | 要求用户再去原站保存一次 |
| 确认/归档事件 | 更新统一处理记录；需远端操作时按真实能力执行并验证 | 改变人工状态即宣称故障恢复 |
| 静默提醒 | 按选定对象、渠道、期限更新实际发送策略并验证 | 只关闭本机提醒却报告所选渠道全部静默 |
| 暂停同步/移除接入 | 显示实际影响与数据保留结果，按所选业务动作执行 | 暗中删除服务器、卸载探针或清除历史 |
| 接入并验证 | 一个向导完成适用的授权、保存、认证与发现步骤；恢复断点 | 在原站登录成功就视为 API 授权与持久化成功 |
| 执行远程任务 | 原生确认、OperationJob、真实执行、后态验证和单一结果页 | 通过原站执行却伪造完整的本地确认记录 |

各项完成以真实目标状态为准。适配器缺少 API、权限或兼容性时，保留用户修改并在原生流程提供错误与恢复路径；需要协议扩展或支持版本升级的能力仍是交付缺口，不能把“请去服务器后台操作”作为完整接管方案。授权和凭据用途保持隔离，原生体验不意味着秘密可以任意复制。

## 9. 告警与通知的统一策略

客户端提供一套事件与通知体验，内部保留四类事实：

1. 规则配置：可按后端能力原生编辑，但规则数量不进入待处理故障数。
2. 真实远端事件：保留稳定事件 ID、对象、状态和时间，支持的处置操作纳入统一任务。
3. 客户端观测事件：后端没有事件 API 时，可由有效时间戳的观测与规则生成事件；保留证据与实际来源，不伪造远端事件 ID 或确认结果。
4. 人工处置：确认、备注、归档及 OperationJob 附着于统一事件，真实恢复由新的有效观测确认。

同一问题可聚合呈现，但不能仅按标题或主机相同删除来源事件。聚合保留各来源证据、恢复条件和审计；人工处置不能替未知或仍异常的来源宣布恢复。日常界面表达“异常状态 + 处理状态”，技术来源在详情中可追溯，不要求用户在两套告警列表协调状态。

一套通知策略统一管理渠道、发送职责、静默期限和投递结果。同步到不同执行端属于内部编排，任何未生效目标都应显现并可重试；在没有真实契约和验证前不能承诺跨端去重或静默已完成。迁移保留现有规则、渠道与投递账本，不擅自关闭已有渠道，也不重放历史通知。

## 10. 推进方式与规划边界

PRD 0.5 第 11 节的 A–D 阶段是统一开发计划；本审计不另外建立一套阶段定义。先阻断已复现的告警语义错误，再按依赖补齐原生入口、统一对象、双向同步和完整管理闭环。页面收敛与品牌弱化可以提前交付，但不能据此声明完成接管。

每一阶段都要用同一用户操作验证数据与结果，而不只验证页面出现。后端能力矩阵应记录支持版本、真实读写 API、权限与故障恢复方式；未实现或不可验证的能力保留为缺口。现有功能、凭据、映射、快照、历史、审计与投递记录采用兼容迁移。0.4 的 CI、内嵌原站和布局结果不能替代 0.5 的同步及原生管理验收。

## 11. 产品验收场景

- 零 Komari 用户完成新增 SSH、终端、SFTP、转发，流程保持连续；无需了解节点、Agent Token 或监控服务器，无虚假监控告警。
- 已有后端、零 ShellBeam 主机：原生接入发现节点后，可原地导入为纯监控主机或关联已有主机；之后添加 SSH 仍保留同一主机、告警与审计身份。
- 同一 Vault 接入后端时，未关联主机保持原体验；关联主机在原有工具和设置中获得监控能力，不出现第二份日常目录。
- 原生界面编辑共享主机名一次，所有选定目标读回一致；远端外部改名后同步回同一主机，无需第二次保存或第二套设置。
- 远端写入成功后丢失响应并重启客户端：能够确认实际结果，只有一次业务变更和一项逻辑任务，不重复执行危险动作。
- 两端并发编辑且设备时钟不同：不同字段合并，同字段冲突在原生界面解决；失败修改可恢复，旧快照不覆盖新值。
- 明确排除自动匹配或删除关联后，刷新、同步、重启与离线队列恢复均不自动接回；后端替换、Vault 锁定阻止旧任务误发。
- 禁用离线通知规则、未触发规则和缺少事件证据均不产生当前故障；active=0 不因规则数大于零变成 active；已有错误记录保留可追溯审计，不伪造恢复。
- 真实异常的确认与静默均从统一入口完成：处理状态不冒充健康恢复，所选通知渠道确实生效或明确显示可恢复的部分失败。
- 编辑规则、通知或服务配置只使用原生设置；一个保存流程完成规定的写入和验证，不以跳转原站、用户自行保存两次或记住存储位置作为验收。
- 暂停/移除接入时，SSH、探针、历史与凭据的实际影响符合所选动作；不因菜单收敛删除已有数据。
- 主机列表、资产视图、Workspace 对同一来源采用一致投影、单位、样本时间和回退规则；不同来源或时间的合法差异可解释，历史不伪装成实时。
- 每项原生操作只有一个权威详情，主机/活动/告警中的入口不重复生成任务；外部历史保留真实来源。
- 原生接入、探针与服务管理按支持版本完成实际任务；过渡原站只用于调试，不计入完成证据。
- 真实用户无需理解后端产品边界，即可完成“添加主机、编辑资料、配置监控、处理异常、查看结果”；体验验收同时核对相关目标的一致性与失败恢复，不能只用代码覆盖率代替。
