# Local rules and continuous endpoint checks

ShellBeam owns an application-level `LocalOpsRuntime`, registered beside its monitor runtime. TCP and HTTP checks continue when the health panel or Workspace closes, while the app stays open and the selected vault is unlocked. Locking/switching the vault stops publishing previous in-flight work; closing ShellBeam stops these SSH agentless checks. This scheduler is separate from the optional resident Probe.

Endpoint definitions and the latest 500 safe result rows are stored per vault and host. Each enabled check is due at `nextCheckAt`; restart hydration honors that deadline, and shortening an interval advances it. Manual and automatic checks share a four-connection gate and deduplicate the same in-flight check. Each sweep considers at most 64 oldest due checks. Workspace displays retained results, result history, observation freshness and the direct/ProxyJump path.

HTTP checks execute `curl` on the selected server; TCP checks execute `nc` (or a bounded Bash TCP fallback) on that server. They therefore test connectivity **from the selected server** to the configured endpoint. All SSH commands use the common Workspace transport and an explicit vault scope. A transport/auth/host-key error is unknown; an executed endpoint check can report failing. Unknown never reports a passing check or resolves an incident.

Local rules support CPU, memory, root filesystem disk usage, and named systemd service units. Resource rules consume canonical fresh ProbeProvider observations. Service checks query the exact allowlisted unit through the same Workspace transport; absent systemd/units, transitional states and failed transport remain unknown. A service is failing only on an observed `inactive` or `failed` state. Rules allow threshold, recovery threshold (hysteresis), trigger duration, recovery duration, and warning/critical severity. There are at most 32 configured rules per host.

Trigger and recovery durations advance only on new, fresh samples. Replaying a cached sample does not advance time. Unknown samples or a gap beyond the freshness allowance reset pending evidence but preserve active/acknowledged incidents. Reloading preserves incidents and immutable audit rows but requires new sustain evidence. Disabling/removing a rule stops evaluation but retains existing incidents. Closing an incident is a separate confirmed operation and does not manufacture a successful remote observation.

Endpoint failures use the same persisted local alert lifecycle, with configurable failure/recovery duration. Active alerts can be acknowledged or closed in the host health panel through the canonical `OperationJob` confirmation flow. Rejected consent is audited without mutation. The native transaction validates the exact vault, host, rule, action, running job and confirmed consent, then stores its `operationJobId` on both the alert and immutable lifecycle audit. Audit history survives sessions. The shared notification dispatcher handles local/system/webhook policy, recovery routing, redaction and diagnostics. Event identities are immutable; delivery is deduplicated across concurrent refreshes and reloads. Only failed channels retry, no more than four attempts, at least 60 seconds apart, for lifecycle events no older than 24 hours. Newly enabled channels do not backfill previously handled events.

The desktop uses `local_ops_documents` in the existing `workspace_inventory.sqlite3` as canonical storage, keyed by vault, host and document kind. Ownership is checked against the vault’s saved hosts. Strict field allowlists and bounded rows reject arbitrary payload/output fields. Revision checks reject stale writes and rehydrate the canonical state instead of overwriting a peer acknowledgment. Native persistence failures are visible, and no notification claims a newly durable transition before persistence succeeds. The renderer localStorage is a scoped mirror/migration source; browser previews use it without a native backend. Persistence retains allowlisted configuration, result counters/fixed error codes, alert lifecycle rows and audit metadata. It does not retain authentication secrets, command output, HTTP response bodies or provider payloads. Local rule data is independent of Komari alerts; a local threshold does not mutate the Komari server's state.

MCP `get_server_alerts` and `get_server_probe_state` expose a scoped `localOps` observation containing alerts, immutable audits and the latest 500 safe health results. Canonical OperationJobs/audits are joined from their job references under the existing client, vault and host grants. Task commands, credentials and configuration payloads are not returned by this observation.

`ScheduledOpsRuntime` separately owns app-level recurring commands across Workspace navigation. Enabling presents the host, route, command, interval and impact, records confirmed consent in an OperationJob, and grants an in-memory permission bound to vault, host, task, command and interval. The enabled state and running intent must reach native storage before a command is sent. Automatic/manual executions share a two-command limit. Locking/changing the vault, application restart, or an interrupted/unknown execution pauses schedules and revokes session permission; explicit enabling resumes at a future deadline rather than replaying missed writes. Closing ShellBeam stops this scheduler; it does not install cron or an OS background service.
