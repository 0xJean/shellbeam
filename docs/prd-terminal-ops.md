# Terminal + Ops 产品 PRD

状态：实施中，按验收清单核对交付
版本：0.4
日期：2026-10-20

实施与验收状态见 [Terminal + Ops 验收矩阵](./terminal-ops-acceptance.md)。功能存在、自动测试通过、平台实机验收和正式发布分别记录，不互相代替。
产品：ShellBeam

## 1. 产品判断

ShellBeam 不再只定位为 SSH 终端，而是定位为 **Terminal + Personal Ops Control Plane**：用户连接服务器后，可以在同一个主机上下文中完成观察、诊断、操作和验证。

Terminal 仍然是通用入口，Workspace 是面向常见运维任务的可视化层。两者共享主机、Vault、连接状态、探测结果和操作记录。

ShellBeam 不在第一阶段复制完整的 Komari/RMM 平台，也不把 Komari 探针强制安装到用户服务器。Komari 作为可选数据源和集成对象；需要持续采集时，再通过明确授权接入 Komari Server 或可选常驻探针。

2026-10-20 集成体验修订：**用户围绕主机完成任务，Komari 为已关联的主机提供可选数据。** ShellBeam 的终端、SFTP、端口转发和 SSH 运维不依赖 Komari；接入一个服务不能把整个 Vault 切换为“Komari 模式”。原站控制台只用于高级管理，不能用在 App 内打开整套原站代替产品集成。以下产品结构、第 7、9 节及 Phase 2 收敛计划采用 0.4 规则；旧功能测试、0.3 及此前实机结果仍保留，不自动代表本次修订已验收。

## 2. 立项时背景与现状（2026-10-16）

当前代码已经具备运维控制台的基础：

- 通过 SSH 采集 Linux 的 CPU、内存、磁盘、网络、负载和 uptime，并在本地保留 24 小时历史。
- 资产盘点可以发现系统工具、systemd 服务、Docker 容器和项目清单。
- Workspace 已有资产、文件、进程、服务、日志、工具管理和终端跳转入口。
- MCP 已提供服务器资产、指标、一次性探测、SSH 命令和 SFTP 能力。

当前实现仍有明确边界：

- 没有真正的 Komari API、Server 或 Agent 集成。
- 监控依赖 ShellBeam 进程运行，应用退出后停止采样。
- 监控、资产盘点和 MCP 探针存在重复采集逻辑。
- 没有统一告警、通知、持久化操作任务或服务健康模型。
- ProxyJump 已覆盖终端、SFTP 和端口转发，但 Workspace 运维命令和 MCP 探针尚未全链路支持。
- 当前探测和运维能力以 Linux 为主，Windows、macOS、FreeBSD 的数据缺失不能直接解释为离线。

## 3. 目标用户与核心场景

### 目标用户

- 管理个人 VPS、家庭服务器和小型实验环境的开发者。
- 需要在桌面和移动端快速排查服务器问题的个人运维者。
- 使用 SSH、SFTP、端口转发和 AI 辅助命令完成部署与维护的用户。

### 核心场景

主要使用终端的用户无需完成监控接入，也无需理解 Provider、节点映射或 Agent 发布。需要运维能力时，使用原有 SSH 功能；需要复用现有 Komari 时，再为具体主机关联节点。

1. **发现问题**：从主机列表看到磁盘、内存、服务或探测状态异常。
2. **定位问题**：打开 Workspace 查看进程、服务、端口、日志和最近指标。
3. **执行处理**：跳转终端、SFTP 或执行带确认的运维动作。
4. **验证结果**：重新采样、查看服务状态和操作结果，确认问题是否缓解。
5. **跨网络管理**：目标主机通过 ProxyJump 连接时，所有上述能力仍然可用。

## 4. 产品范围

### 本期范围

- Terminal 与 Workspace 双模式。
- 统一的远程连接传输层，覆盖直连和 ProxyJump。
- 统一 ProbeProvider 抽象，整合 SSH Agentless 和 Komari 数据。
- 主机列表运维视图。
- Linux 主机的资源、资产、进程、服务、日志和端口观察。
- 受确认、幂等和审计约束的常见运维动作。
- 本地告警规则和通知入口。

### 明确不在首期范围

- 团队协作、RBAC、审批流和企业合规控制台。
- 自动安装软件、自动发布、自动回滚和无人值守自愈。
- 完整日志分析平台、APM、SLO 管理或 Kubernetes 控制面。
- 默认在服务器安装 ShellBeam 或 Komari 常驻 Agent。
- 将用户 SSH 凭据上传到云端。

## 5. 产品结构

每个主机上下文包含两个一级模式：

- **Terminal**：交互式 SSH、命令历史、AI 命令、会话日志。
- **Workspace**：Overview、Files、Processes、Services、Logs，以及返回 Terminal 的入口。

Workspace 的每个操作都必须映射到可解释的 SSH、SFTP 或端口转发能力。用户可以从任意页面回到 Terminal，不能被可视化流程锁住。

### Workspace 首期页面

| 页面 | 职责 | 首期能力 |
| --- | --- | --- |
| Overview | 判断主机状态和推荐下一步 | 一组资源指标、简洁来源/采样时间、真实异常与最近操作；技术诊断按需展开 |
| Files | 文件查看和维护 | 浏览、上传、下载、重命名、权限、跳转终端 |
| Processes | 进程观察 | 搜索、排序、资源占用、查看详情、确认后终止 |
| Services | systemd 服务管理 | 状态、启动、停止、重启、启用、日志 |
| Logs | 日志排查 | journalctl、文件日志、搜索、过滤、跟随、复制 |
| Terminal | 通用处理入口 | 复用现有终端和会话上下文 |

后续再增加 Docker、Network、Sites、SSL 和 Scheduled Tasks。

### 0.4 渐进展示与设置归属

- Overview 只展示一组当前资源值，不为 SSH、Komari 和 Agent 分别复制卡片。来源、原始采样时间及回退说明集中一处，不在每个指标卡重复健康、重试和耗时。
- 未采集资源时使用一个中性空状态，说明终端、文件和 SSH 运维仍可使用；未启用的能力不生成“未知故障”卡片。实际监控中断、过期和读取失败仍提供简洁可见提示，不据此判定 SSH 离线。
- Provider ID、节点 ID、TTL、可信程度、接收/同步时间、采集重试放入按需详情。指标历史在用户打开后加载；收起不删除历史或停止后台采集。
- 未使用 Agent 的主机只保留主动打开监控工具的入口，不默认挂载安装、升级、制品审核和回灌面板。已有 Agent 记录可从管理入口查看；实际异常保留简洁提示，未安装、已退役或不支持不作为当前故障。
- 主机或 Vault 切换关闭详情和管理视图，包括 A→B→A；旧上下文的异步结果不能显示在新上下文或继续旧操作。
- 设置分为“常规”“连接与终端”“监控与通知”“集成”“高级”，默认打开常规。语言、外观和 Vault 设置不被监控接入淹没；通知与采集策略、Komari 数据源、Agent 发布分别归入对应分类。
- “集成”展示已保存数据源或简短添加入口；只有点击添加或编辑后才显示 Komari 接入向导，保留原凭据引用、配置 ID 和手动映射。

## 6. 统一 ProbeProvider

### 6.1 设计目标

所有指标、资产和健康数据都通过统一 Provider 获取，避免 server monitor、workspace inventory 和 MCP probe 各自维护一套脚本、解析器和状态机。

Provider 必须返回来源、采样时间、数据新鲜度和可信程度。缺失值表示未知，不得自动转换成零或健康。

### 6.2 Provider 类型

| Provider | 连接方式 | 适用场景 | 首期策略 |
| --- | --- | --- | --- |
| `ssh-agentless` | ShellBeam 通过 SSH 执行只读探测 | 无需安装、临时主机、个人用户 | 保留并统一 |
| `komari` | Komari API/Server | 已经使用 Komari 的用户 | 只读适配器优先 |
| `shellbeam-agent` | 可选常驻探针 | 应用关闭后仍要采集 | 后续评估，不默认安装 |

### 6.3 统一数据模型

核心实体至少包含：

- `HostIdentity`：hostId、地址、端口、用户名、跳板链、主机密钥身份。
- `ProviderRef`：provider 类型、远端节点 ID、endpoint、能力列表。
- `MetricSnapshot`：CPU、内存、磁盘、网络、load、uptime、采样时间。
- `InventorySnapshot`：OS、架构、工具、服务、容器、监听端口、项目发现结果。
- `HealthState`：online、stale、offline、paused、unsupported、unknown。
- `Freshness`：sampledAt、receivedAt、TTL、过期原因。
- `Confidence`：observed、partial、inferred；默认使用 observed 或 partial。
- `Alert`：规则、状态、首次触发、最近触发、确认状态和关联主机。
- `OperationJob`：动作、参数摘要、状态、开始结束时间、结果摘要、审计 ID。

### 6.4 采集调度

- Agentless 默认 60 秒采集资源指标，资产盘点使用较低频率或按需刷新。
- 同一主机同一时间只允许一个相同类型的采集任务。
- 采集并发、超时、输出大小和历史保留时间必须集中配置。
- Provider 失败时保存失败原因和最后成功时间，不覆盖较新的成功数据。
- 采集结果可被 UI、MCP 和命令面板共同读取。

## 7. Komari 集成

### 7.1 集成定位

Komari 集成是可选能力，不改变 ShellBeam 的本地优先设计。ShellBeam 消费 Komari 的节点、指标和可用告警信息，在同一个主机上下文完成观察、SSH 诊断、确认操作和结果验证。

| 能力 | 产品归属与入口 |
| --- | --- |
| 主机身份、Terminal、Files、Services、Processes、操作审计 | ShellBeam 的统一主机/Workspace；复用 Vault、SSH/ProxyJump 和 OperationJob |
| Komari 实时指标与历史 | 主机 Overview，保留简洁来源、采样时间和数据状态 |
| 告警处理 | 主机告警及统一事件视图；数据源作为筛选和诊断信息 |
| 地址、认证、节点映射 | 设置中的“集成 → 监控数据源 → Komari”，不占据主机首页 |
| Provider ID、节点 ID、TTL、接收/同步时间、重试 | 可展开的数据源诊断详情 |
| Komari 原站 | 数据源的高级管理入口，桌面使用主窗口内可关闭的管理面板 |

未配置 Komari 的用户以及已配置服务但尚未关联的主机，不显示 Komari 专属空面板，也不要求安装探针。Komari Agent 与 ShellBeam Probe 是不同的可选采集方式，不能因接入其中一个而要求同时安装另一个。

| 使用情况 | 主机页 | Workspace |
| --- | --- | --- |
| 仅终端、SFTP、端口转发 | 默认连接视图，保留连接与原有主机信息 | 原有 SSH 功能可用，无 Komari 接入要求 |
| 有 SSH 监控，没有 Komari | 可选监控摘要，真实告警在两种视图均可达 | 使用 SSH 资源、服务、进程和日志；无需安装 Agent |
| 主机已关联 Komari | 沿用同一主机条目与告警入口 | 在同一组指标中采用有效 Komari 数据，保留简洁来源；可用 SSH 数据按规则回退 |
| Vault 有 Komari，但此主机未关联 | 保持此主机原体验 | 不借用同 Vault 其他节点的数据，不提示此主机 Komari 故障 |

### 7.2 首期功能

- 添加 Komari Server endpoint。
- 使用 token 或用户明确提供的 API 凭据访问。
- 拉取节点列表、节点状态、指标时间序列和告警摘要。
- 将 Komari 节点映射到 ShellBeam 主机，可手动确认或按地址匹配。
- 在用户选择的监控摘要和 Overview 显示简洁的数据来源和更新时间；连接视图不强制增加资源/来源列，完整同步/能力详情按需展开。
- Komari 数据不可用时，允许回退到 SSH Agentless；回退必须显示来源变化。
- 日常接入、节点关联和运维不依赖 Komari Web 控制台；高级管理保留原站入口及来源说明。

### 7.3 原生接入与主窗口体验

已有 Komari 的接入路径为：**填写地址/凭据 → 保存并验证连接、发现节点 → 关联已有主机 → 完成**。

- 接入向导仅由“添加数据源”或已保存数据源的“编辑”打开；进入设置或集成分类本身不强制展开向导。
- 保存配置、认证成功、发现节点、已有真实采样是不同结果，必须分别表达。
- 编辑现有连接复用已保存的凭据引用；验证时由 Vault 安全读取，界面不回显或要求导出 Key，不因导航强制重填。
- Vault 锁定、切换、退出及过期异步结果不得污染新上下文。
- 映射使用现有手动优先、冲突检测和版本检查，保留一对一约束及已有绑定。
- 主机卡默认保持连接和告警入口；用户可选择监控摘要。Grid 与 List 均显式展开运维详情，关键异常和处理入口仍可达。
- 桌面高级控制台留在主窗口中，按 Vault 和集成作用域管理，关闭/锁定/切换时收起；重复点击不能持续创建独立窗口。
- 移动端日常接入使用原生界面；平台尚不支持内嵌管理时，只有高级原站管理明确交给系统浏览器。
- 初始化新 Komari Server 是可选的高级部署流程，不属于已有服务接入的必经路径。仅对支持的 API 实现原生表单，不承诺绕过上游登录或授权。

### 7.4 告警聚合与状态语义

- 连接可达性、监控数据状态、服务健康分别表达。没有 Komari 观测不能推断 SSH 离线；`unknown` 不能映射为 `offline`。
- 未启用数据源、未关联节点或未安装 Agent 是可选能力未使用，不新建对应故障告警；已有历史不因此删除。
- 首次尚无有效样本显示“等待首次上报”，不把无数据、未知状态和重试耗尽分别升级成多条严重告警。
- 曾有有效样本后中断，按照新鲜度和错误语义呈现一次监控事件；状态、指标错误、重试次数作为该事件的诊断成员。
- 聚合范围包括集成、节点、主机及故障类别。不得合并不同节点、独立资产盘点故障或远端规则告警。
- 用户事件、通知和确认/关闭动作采用同一聚合规则；仅折叠 UI 而仍发送多条通知不算完成。
- 主机卡片的告警计数来自本地聚合事件。远端服务器的规则告警总数单独标注，不能与本地事件数混成一个统计口径；既有 API 的远端摘要字段保持兼容。
- 确认/关闭只表示 ShellBeam 本地处理。只有新的有效真实观测可以证明恢复；关闭告警、SSH 操作成功或重新读取缓存均不能证明 Komari 恢复。
- 原始告警 ID、生命周期审计、通知投递账本及 OperationJob 关联保留；旧 ID 查询/动作继续兼容。聚合不能通过删除历史或重建全部 ID 实现。停用或解绑来源的记录仍能通过“包含历史记录”查看原状态和审计，并标注为非当前数据源，不计入待处理摘要，也不重新触发通知。
- 主机页使用统一告警中心，支持按主机、来源及生命周期筛选；不再把 Komari 告警单独铺成首页的一套事件列表。主机卡保留待处理数量和详情入口。统一展示继续调用原有确认、关闭、恢复与 OperationJob 流程，不将不同来源记录强行改成同一身份。

### 7.5 当前数据源资格与历史保留

- 主机列表与 Workspace 共用当前源判定：同 Vault、已启用的集成、当前节点/主机关联以及匹配的 endpoint。
- 停用、解绑、重绑或修改 endpoint 后，旧快照退出当前指标、状态和当前告警摘要。不能因专用缓存已清空而从 canonical 缓存复活旧关联。
- 映射修改以原生 revision 为准；只有可证明未编辑的旧关联才能采用明确的兼容路径。映射状态读失败不得等同于“尚未配置映射”。
- 保留持久化历史、原始告警与 OperationJob；历史记录可查不代表它仍是当前数据源。重新启用或绑定后重新核验资格及原始采样 TTL，不把缓存读取当成恢复。
- 这些规则限定当前展示、来源选择与告警投递资格，不擅自删除凭据、重写历史、改变采集频率、关闭通知设置或自动安装 Agent。

### 7.6 首期不做

- 通过 ShellBeam 自动部署 Komari Server。
- 自动在远端安装、升级或卸载 Komari Agent。
- 把 Komari 指标直接当作 SSH 操作成功的证明。
- 通过 Komari API 执行重启、发布或任意命令。
- 复制或维护整套 Komari 前端，或将其整站作为 ShellBeam 的第二套日常导航。

### 7.7 后续常驻探针策略

如果用户需要 ShellBeam 关闭后仍保持采集，应提供明确的“安装探针”流程：展示安装命令、权限、版本、网络访问、卸载方式和风险；安装前要求用户确认，安装后记录版本、节点 ID、最后心跳和能力。探针更新必须支持版本检查、失败回退和卸载。

## 8. ProxyJump 全链路

### 8.1 支持范围

同一份主机连接配置必须适用于：

- Terminal 交互会话。
- SFTP 文件操作。
- 本地、远程和 SOCKS 端口转发。
- Server Monitor 指标采集。
- Workspace 资产、进程、服务、日志和工具动作。
- MCP inventory、metrics、probe、command 和 SFTP 工具。

### 8.2 连接模型

- 目标主机和跳板机分别解析认证凭据与 known_hosts。
- 前端只传递主机引用和操作参数，凭据在 Rust/Vault 层解析。
- 默认支持一个跳板；多跳链路作为后续扩展。
- 跳板或目标主机密钥变化时，连接必须失败并给出明确原因。
- 所有失败都区分目标不可达、跳板不可达、认证失败、主机密钥失败和操作超时。
- MCP、Workspace 和后台采集不能绕过跳板配置直接连接目标地址。

### 8.3 验收标准

- 配置了跳板的主机可以从主机列表启动监控、资产盘点、服务查看和日志查看。
- 同一主机从 Terminal、SFTP、端口转发和 Workspace 看到一致的连接状态。
- 跳板凭据不出现在日志、MCP 参数、UI 状态或操作结果中。
- 跳板断开时，主机显示“跳板不可用”，不能错误显示为目标主机离线。
- 自动化测试覆盖直连、单跳、认证失败和主机密钥变化。

## 9. 主机列表运维视图

主机列表首先负责选择主机和快速连接，再按用户需要显示运维信息。没有保存展示偏好时，默认连接视图；不得因配置了 Komari 或已有后台数据而自动扩展页面。

### 9.1 连接视图与监控摘要

- 连接视图桌面表格为五列：序号/选择、主机、地址、状态/告警、操作。主机中保留用户名、分组/标签及直连/ProxyJump 路径；未采集时不铺资源占位或 Provider 诊断。
- “显示监控摘要”是独立的本地展示偏好，按需扩展为九列：序号、主机、地区、地址、更新、资源、运维、状态、操作。表头与主行共用对应列宽；已有数据按来源/采样语义显示，不能补造数值。
- 开关只改变信息密度，不能启停采集、告警、通知、Provider 或 Agent。折叠详情也不改变后台行为。已保存的展示偏好应保留。
- Grid 与 List 使用同一信息层级：常用连接入口、有效资源摘要、真实异常和告警计数；告警明细、服务/进程列表、审计及监控诊断放入默认收起的详情。List 详情占整宽，展开不能撑高某个单元格或改变主行高度。
- 未配置或未关联的主机不显示 Komari 空模块；未观察的资源不出现四块“未知”诊断。真实监控异常和待处理告警在连接视图中仍有入口。
- 主机/Vault 或展示模式切换后收起详情，不能返回旧作用域时自动重开；当前记录和审计继续可达。

### 9.2 搜索与筛选

- 名称、地址、用户、分组、标签、跳板机。
- Provider、操作系统、状态、告警级别和能力。
- 资源阈值，例如磁盘大于 80%。
- 数据新鲜度，例如超过 5 分钟未采样。

高级运维筛选按需打开，不默认占据主机页；切换展示方式不暗中改变已有筛选语义。批量控制只在用户进入批量选择后显示，选择框的单击、双击和键盘操作不能触发终端连接。

### 9.3 快速动作

- 打开 Terminal。
- 打开 Workspace Overview。
- 刷新探测。
- 打开 Files、Services、Logs。
- 查看告警。
- 执行经过确认的常见动作。

首期不提供无确认的跨主机批量重启、批量删除或批量写入。

## 10. 运维动作与安全

### 动作分级

| 级别 | 示例 | 规则 |
| --- | --- | --- |
| 只读 | 查看状态、进程、服务、日志、端口 | 默认允许，结果持久化摘要 |
| 低风险写入 | 创建目录、上传文件、启动服务 | 明确目标，用户确认 |
| 高风险变更 | 删除文件、停止/重启服务、安装/升级 | 强确认，显示影响范围和命令摘要 |
| 自动化 | 定时任务、批量动作、自愈 | 首期不做 |

所有动作都使用 `OperationJob`：queued、running、completed、failed、unknown、cancelled。超时或断开时显示 unknown，不能假设远端动作已经停止或失败。

MCP 沿用按客户端、Vault、主机和能力授权的模型。SSH 账号权限不是安全沙箱；文档和 UI 都应建议使用最小权限账号。

## 11. 分阶段开发计划

### Phase 0：统一基础（P0）

目标：先把所有运维入口建立在同一连接和数据语义上。

- 统一 SSH/SFTP/ProxyJump transport。
- Workspace 和 MCP 全链路传递跳板配置。
- 抽象 `ProbeProvider` 和统一数据模型。
- 合并重复的监控、资产和 MCP 探测解析逻辑。
- 统一状态、采样时间、来源、错误和能力字段。
- 完成直连、单跳、Vault 锁定和主机密钥错误测试。

验收：配置跳板的主机可以完成监控、资产、服务、日志、MCP 查询和终端操作；不同入口不再出现连接能力不一致。

### Phase 1：Ops 闭环（P1）

目标：从“看指标”升级为“发现问题并处理”。

- 完成主机列表运维视图。
- 增加 Processes、Services、Logs 的稳定只读能力。
- 增加端口和 HTTP/TCP 健康检查。
- 增加本地规则告警、去重、确认和恢复状态。
- 增加操作任务、结果摘要和本地审计。
- 每个异常提供 Terminal、Files、Services 或 Logs 的下一步入口。

验收：用户能够从主机列表发现一个异常，进入诊断页面，执行确认后的动作，并看到重新采样后的结果。

### Phase 2：Komari Adapter（P1/P2）

目标：兼容已有 Komari 用户，减少重复部署和数据孤岛。

- 配置 Komari Server 和 token。
- 节点发现、主机映射、指标和告警同步。
- 在可选的主机监控摘要与 Overview 中显示数据来源和同步时间。
- SSH Agentless 与 Komari 共享主机视图，保留来源并可回退；多来源诊断按需展开。
- Komari API 错误、权限错误和节点映射冲突提供可解释状态。

验收：用户可以在不安装新 Agent 的情况下，把已有 Komari 节点导入 ShellBeam，并从告警跳转到 SSH/Workspace 处理。

#### Phase 2 体验收敛（0.4，2026-10-20 修订）

按以下顺序实施，保留原集成 ID、凭据引用、映射、快照和审计：

1. **默认主机页与按主机能力**：连接视图五列为默认，九列监控摘要按需；Grid/List 同样折叠详情，保留有效异常和连接入口。共用数据源资格，停用/解绑/改 endpoint 后旧缓存不再占用当前状态。
2. **统一详情体验**：Overview 只呈现一组资源和一处来源说明；技术诊断、Agent 管理及指标历史按需展开，跨作用域收起且拒绝迟到结果。
3. **告警与设置归属**：告警中心统一来源/主机筛选和原有操作闭环；设置分类，Komari 仅在添加/编辑时展开接入流程，沿用凭据和映射。
4. **对应版本验收**：覆盖未配置、SSH-only、Komari 已映射与同 Vault 未映射、停用/解绑/endpoint 变更及 A→B→A；在当前 head 的安装包中验证两种主机视图和真实告警操作，再记录 CI/实机证据。

验收：

- 已有 Vault 升级后无需重新输入凭据或重新关联主机，原审计任务仍可查询。
- 未保存展示偏好的用户进入五列连接视图；没有 Komari 也可完整使用终端、SFTP、转发和 SSH 运维，不显示 Komari 专属空模块或 Agent 安装面板。
- 接入后查看监控、告警、诊断和操作均可在 ShellBeam 主窗口完成。
- 监控摘要开关保留当前采集及通知设置；List 五/九列与表头一致，Grid/List 都通过显式展开访问诊断、确认和审计，展开详情不改变 List 主行高度，切换主机或 Vault 后收起。
- 全局配置 Komari 不影响未关联主机；停用、解绑或改 endpoint 后不使用旧缓存作为当前指标/告警，原凭据、历史与审计仍保留。
- 桌面多次打开同一高级管理入口不会新增顶层窗口，锁库/切换后不会遗留旧作用域的可见管理界面。
- 首报等待不会产生三条同根因通知；真正中断只显示一个对应事件，独立故障仍分别可见。
- 旧通知不因升级/重载重放；确认/关闭有 OperationJob，原成员 ID 和历史审计保持可追溯。
- 新鲜有效观测触发恢复，未知或缓存数据不制造“已恢复”。

### Phase 3：可选常驻探针（P2）

目标：支持应用关闭后的持续采集和更丰富的远端能力。

- 明确授权的探针安装、升级、卸载和版本检查。
- 心跳、离线、能力和版本状态。
- 本地缓存或 Komari Server 继续接收历史数据。
- 探针权限说明、最小权限模式和卸载验证。

验收：用户能看到探针生命周期和最后心跳；探针不可用时不会伪装成 SSH 在线或健康。

### Phase 4：扩展运维（P3）

- Docker/容器管理。
- Sites、SSL 和 Scheduled Tasks。
- Webhook、系统通知和更丰富的通知策略。
- 多主机编排和有限批量操作。
- 在实际用户需求稳定后，再评估团队权限、远端服务和云同步。

## 12. 质量与成功指标

### 质量门槛

- 所有 Provider 都返回来源、采样时间和 freshness。
- 监控数据缺失不会显示为零。
- 运维动作有确认、超时、unknown 状态和审计摘要。
- ProxyJump 与直连使用同一套功能测试。
- 不记录密码、私钥、token、完整命令输出或敏感文件内容。

### 产品指标

- 主机列表到首次有效诊断的步骤数不超过 3 步。
- 发生告警后能在同一主机上下文打开 Terminal、Logs 或 Services。
- 配置跳板的主机与直连主机拥有相同的运维功能覆盖率。
- 采样失败原因可理解，且不把过期数据误报为在线。
- Agentless、Komari 和未来 ShellBeam Probe 的来源可被用户清楚区分。

## 13. 主要风险与决策点

- **范围膨胀**：继续保持个人运维工作台定位，暂不进入企业 RMM、RBAC 和全自动发布。
- **权限风险**：所有写操作默认确认；推荐专用低权限 SSH 用户；不把 Agent 安装做成隐式行为。
- **数据可信度**：展示来源、新鲜度和 partial/unknown 状态，避免把资产发现当作应用健康证明。
- **连接复杂度**：ProxyJump 必须先在统一 transport 中解决，否则每增加一个运维模块都会重复出现连接分叉。
- **持续监控成本**：先支持 Komari Adapter，再根据用户需求决定是否维护自己的常驻探针和后台服务。

## 14. 首个实现切片

建议第一个开发切片只包含：

1. `RemoteTransport` 支持 direct/ProxyJump。
2. `ProbeProvider` 接口和 `ssh-agentless` 实现。
3. Workspace monitor、inventory 和 MCP 迁移到统一 Provider。
4. 主机列表增加 Provider、freshness、alert、capability 字段。
5. 补齐单跳主机的监控、资产、服务、日志和 MCP 测试。

完成这个切片后，再进入 Komari Adapter，避免在连接和数据模型尚未统一时直接叠加第三套探测协议。
