## 1. 产品判断

ShellBeam 不再只定位为 SSH 终端，而是定位为 **Terminal + Personal Ops Control Plane**：用户连接服务器后，可以在同一个主机上下文中完成观察、诊断、操作和验证。

Terminal 仍然是通用入口，Workspace 是面向常见运维任务的可视化层。两者共享主机、Vault、连接状态、探测结果和操作记录。

**ShellBeam 提供完整的客户端体验，Komari 是可选的监控与运维后端。** 用户只需要理解主机、监控、告警、任务和设置，不需要学习两套产品导航，也不需要到两边分别保存同一个修改。接入后端、同步共享数据、处理冲突和恢复失败是 ShellBeam 的责任。

用户可以始终只使用终端、SFTP、端口转发和 SSH 运维。接入监控后，同一台主机增加持续监控及可用管理能力，保留原有连接方式和页面习惯；不要求同时安装两种探针。

2026-10-21 方向修订：0.5 替代“Komari 只读数据源 + 独立高级管理网站”的长期产品方案。主机、设置、告警及后端管理均由 ShellBeam 原生界面承接，共享业务字段按契约双向同步。Komari 名称主要用于选择后端、安装兼容探针和高级诊断；日常菜单与卡片采用用户任务名称。上游服务仍可独立运行，但其技术边界不能转化为第二套客户端工作流。

本修订是新增产品契约，**不代表已实现完整原生管理或双向同步**。0.4 的可选监控、紧凑布局、数据隔离和历史保留继续有效；其测试、CI 与内嵌原站结果不算作 0.5 完成证据。重复功能与已确认缺陷见 [集成体验审计](./komari-integration-experience-audit.md)。

## 2. 立项时背景与现状（2026-10-16）

立项时的代码已经具备运维控制台的基础（以下保留当时状态，非当前缺口清单）：

- 通过 SSH 采集 Linux 的 CPU、内存、磁盘、网络、负载和 uptime，并在本地保留 24 小时历史。
- 资产盘点可以发现系统工具、systemd 服务、Docker 容器和项目清单。
- Workspace 已有资产、文件、进程、服务、日志、工具管理和终端跳转入口。
- MCP 已提供服务器资产、指标、一次性探测、SSH 命令和 SFTP 能力。

当时实现仍有明确边界：

- 没有真正的 Komari API、Server 或 Agent 集成。
- 监控依赖 ShellBeam 进程运行，应用退出后停止采样。
- 监控、资产盘点和 MCP 探针存在重复采集逻辑。
- 没有统一告警、通知、持久化操作任务或服务健康模型。
- ProxyJump 已覆盖终端、SFTP 和端口转发，但 Workspace 运维命令和 MCP 探针尚未全链路支持。
- 当前探测和运维能力以 Linux 为主，Windows、macOS、FreeBSD 的数据缺失不能直接解释为离线。

## 3. 目标用户与核心场景

### 目标用户

- 管理个人 VPS、家庭服务器和小型实验环境的开发者。
- 需要在桌面和移动端快速排查服务器问题的个人运维者。
- 使用 SSH、SFTP、端口转发和 AI 辅助命令完成部署与维护的用户。

### 核心场景

主要使用终端的用户无需完成监控接入，也无需理解 Provider、节点映射或 Agent 发布。接入已有监控服务后，已有主机获得监控能力；只有监控、暂未配置 SSH 的主机也可以纳入同一目录，之后补充连接资料时保留身份与历史。

1. **发现问题**：从主机列表看到磁盘、内存、服务或探测状态异常。
2. **定位问题**：打开 Workspace 查看进程、服务、端口、日志和最近指标。
3. **执行处理**：跳转终端、SFTP 或执行带确认的运维动作。
4. **验证结果**：重新采样、查看服务状态和操作结果，确认问题是否缓解。
5. **跨网络管理**：目标主机通过 ProxyJump 连接时，所有上述能力仍然可用。

## 4. 产品范围

### 基础范围与 0.5 增量

- Terminal 与 Workspace 双模式。
- 统一的远程连接传输层，覆盖直连和 ProxyJump。
- 统一 ProbeProvider 抽象，整合 SSH Agentless 和 Komari 数据。
- 主机列表运维视图。
- Linux 主机的资源、资产、进程、服务、日志和端口观察。
- 受确认、幂等和审计约束的常见运维动作。
- 本地告警规则和通知入口。
- 0.5：统一主机目录与原生设置；可选后端的主机资料、规则、通知及服务管理在同一客户端完成。
- 0.5：共享业务字段双向同步、一次保存、持久化待同步任务、冲突处理及跨会话恢复。
- 0.5：支持的后端版本逐项验证原生接入、管理及探针生命周期；完整范围与交付顺序见第 7、11 节。

### 明确不在立项首期范围

- 团队协作、RBAC、审批流和企业合规控制台。
- 自动安装软件、自动发布、自动回滚和无人值守自愈。
- 完整日志分析平台、APM、SLO 管理或 Kubernetes 控制面。
- 默认在服务器安装 ShellBeam 或 Komari 常驻 Agent。
- 将用户 SSH 凭据上传到云端。

## 5. 产品结构

每个主机上下文包含两个一级模式：

- **Terminal**：交互式 SSH、命令历史、AI 命令、会话日志。
- **Workspace**：Overview、Files、Processes、Services、Logs，以及返回 Terminal 的入口。

Workspace 的 SSH 运维复用现有 SSH、SFTP 和端口转发能力。0.5 增加后端管理能力时，同样通过统一动作、确认、OperationJob 和结果验证契约执行，不新增一套厂商终端或任务中心。没有 SSH 配置的主机可以查看监控并补充连接资料，不能用伪造地址或凭据启用终端。

### Workspace 首期页面

| 页面 | 职责 | 首期能力 |
| --- | --- | --- |
| Overview | 判断主机状态和推荐下一步 | 一组资源指标、简洁来源/采样时间、真实异常与最近操作；技术诊断按需展开 |
| Files | 文件查看和维护 | 浏览、上传、下载、重命名、权限、跳转终端 |
| Processes | 进程观察 | 搜索、排序、资源占用、查看详情、确认后终止 |
| Services | systemd 服务管理 | 状态、启动、停止、重启、启用、日志 |
| Logs | 日志排查 | journalctl、文件日志、搜索、过滤、跟随、复制 |
| Terminal | 通用处理入口 | 复用现有终端和会话上下文 |

Docker、Network、Sites、SSL 和 Scheduled Tasks 按后续阶段扩展，既有实现与交付边界见验收矩阵。

### 渐进展示与统一设置（继承 0.4，0.5 调整归属）

- Overview 只展示一组当前资源值，不为 SSH、Komari 和 Agent 分别复制卡片。来源、原始采样时间及回退说明集中一处，不在每个指标卡重复健康、重试和耗时。
- 未采集资源时使用一个中性空状态，说明终端、文件和 SSH 运维仍可使用；未启用的能力不生成“未知故障”卡片。实际监控中断、过期和读取失败仍提供简洁可见提示，不据此判定 SSH 离线。
- Provider ID、节点 ID、TTL、可信程度、接收/同步时间、采集重试放入按需详情。指标历史在用户打开后加载；收起不删除历史或停止后台采集。
- 未使用 Agent 的主机只保留主动打开监控工具的入口，不默认挂载安装、升级、制品审核和回灌面板。已有 Agent 记录可从管理入口查看；实际异常保留简洁提示，未安装、已退役或不支持不作为当前故障。
- 主机或 Vault 切换关闭详情和管理视图，包括 A→B→A；旧上下文的异步结果不能显示在新上下文或继续旧操作。
- 设置仍默认常规。外观、语言、Vault 与连接偏好保留原有位置；“监控与通知”统一管理采集、规则、渠道和已连接的监控服务。原“集成”中的监控入口跳到同一个编辑器，不保留第二份配置。
- 监控服务按用户命名显示；仅添加服务时选择后端类型，编辑时复用已有配置和凭据。单台主机的监控设置也打开同一对象、同一编辑器，并可返回原主机。
- 远端指标保留、服务访问与账户等低频设置置于“监控服务 → 服务管理”，由原生表单承接。按“影响本设备 / 所选主机 / 整个监控服务”解释实际效果，不要求用户先判断属于哪家产品。
- VPS 资产收敛为同一主机目录的资产视图，旧入口兼容跳转；活动与任务使用同一操作详情。布局合并必须同时统一状态读取和写入，不能仅修改标题。

## 6. 统一 ProbeProvider

### 6.1 设计目标

所有指标、资产和健康数据都通过统一 Provider 获取，避免 server monitor、workspace inventory 和 MCP probe 各自维护一套脚本、解析器和状态机。

Provider 必须返回来源、采样时间、数据新鲜度和可信程度。缺失值表示未知，不得自动转换成零或健康。

### 6.2 Provider 类型

| Provider | 连接方式 | 适用场景 | 实施策略 |
| --- | --- | --- | --- |
| `ssh-agentless` | ShellBeam 通过 SSH 执行只读探测 | 无需安装、临时主机、个人用户 | 保留并统一 |
| `komari` | Komari API/Server | 需要复用监控后端的用户 | 已有只读 Provider；0.5 另建管理与同步契约 |
| `shellbeam-agent` | 可选常驻探针 | 应用关闭后仍要采集 | 已有可选实现，不默认安装；正式制品分发单独验收 |

### 6.3 统一数据模型

核心实体至少包含：

- `HostEntity`（0.5）：稳定 hostId、主机资料、可选连接资料和监控绑定；现有 hostId 保持不变。
- `ConnectionProfile`（0.5）：SSH 地址、端口、用户名、跳板链、主机密钥身份和 Vault 凭据引用，与主机身份分离。
- `ProviderRef`：provider 类型、远端节点 ID、endpoint、能力列表。
- `MetricSnapshot`：CPU、内存、磁盘、网络、load、uptime、采样时间。
- `InventorySnapshot`：OS、架构、工具、服务、容器、监听端口、项目发现结果。
- `HealthState`：online、stale、offline、paused、unsupported、unknown。
- `Freshness`：sampledAt、receivedAt、TTL、过期原因。
- `Confidence`：observed、partial、inferred；默认使用 observed 或 partial。
- `Alert`：规则、状态、首次触发、最近触发、确认状态和关联主机。
- `OperationJob`：动作、参数摘要、状态、开始结束时间、结果摘要、审计 ID。
- `BackendBinding` / `SyncRecord`（0.5）：后端实例身份、远端对象 ID、绑定版本、共同版本、字段映射、期望值及同步状态；凭据仅存引用。

ProbeProvider 负责观测读取；后端管理适配器负责能力发现、配置读取和写入；同步协调器负责一致性。三者共享主机身份与 OperationJob，但不能在读取指标时隐式触发配置写入。

### 6.4 采集调度

- Agentless 默认 60 秒采集资源指标，资产盘点使用较低频率或按需刷新。
- 同一主机同一时间只允许一个相同类型的采集任务。
- 采集并发、超时、输出大小和历史保留时间必须集中配置。
- Provider 失败时保存失败原因和最后成功时间，不覆盖较新的成功数据。
- 采集结果可被 UI、MCP 和命令面板共同读取。

## 7. 统一原生客户端与可选后端（0.5 新增契约）

本节是目标设计。当前只读集成、内嵌原站、局部确认和已有缓存不能被描述为这些要求已经完成。

### 7.1 产品承诺

- **一个应用**：主机、监控、告警、文件、终端、任务和设置均使用 ShellBeam 的导航与原生交互。普通工作流不打开另一应用、独立管理窗口或整套后台网站。
- **一个主机对象**：连接、资产、监控是同一主机的资料或能力。可以从多处进入，但修改和结果归于同一对象。
- **一次保存**：适合共享的业务数据由 ShellBeam 同步，用户不需要到服务器后台再保存一次。同步失败保留修改并在当前上下文处理。
- **一份可追溯结果**：用户操作对应一项逻辑 OperationJob，实际执行位置、重试和各目标结果归入同一详情。外部操作可作为外部记录导入，不能伪称由 ShellBeam 执行过。
- **按需启用**：未接入后端时保留原终端工作流；接入只增加相关主机的能力，不切换整个 Vault 的模式，不默认扩展主机行或要求安装另一套探针。
- **弱化品牌**：日常使用“监控”“规则”“通知”“服务管理”等任务名称。连接配置展示用户命名的服务；后端品牌保留在接入选择、探针兼容性、许可及高级诊断中。指标仍显示原始采样时间和数据状态，详细来源可查。

“完整客户端”指每个纳入支持范围的用户任务均能在 ShellBeam 原生界面闭环，不等于把上游菜单、网站主题和插件运行环境整体搬进应用。缺少管理 API 的任务记为待补齐能力，不能以整站 WebView 代替完成。

### 7.2 统一主机与能力模型

- `HostEntity` 使用与名称、IP、账号无关的稳定 ID，保留现有 hostId。SSH 连接资料、资产资料、监控节点和采集源关联到该对象；UI、Workspace、资产视图和 MCP 读取同一投影。
- 一台主机允许有多个连接资料和多个采集来源。每个绑定保存后端实例身份、远端节点稳定 ID、绑定版本及能力；同一 Vault 内，同一实例的同一节点不能被当作多台主机重复管理。不同 Vault 可独立接入同一后端，不跨库合并身份或暴露关联。
- 仅监控主机是有效对象，不需要伪造 SSH 地址、用户名或凭据。以后添加 SSH 资料复用同一 hostId、指标历史、事件和审计；已有 SSH 主机接入监控也不能复制成第二条目录记录。
- 名称或 IP 匹配只能产生关联建议，不能独自证明是同一台机器。首次关联需要可验证的稳定身份或用户在接入流程确认；歧义不得自动合并。显式排除、解绑、删除意图持久化，不能在下一次发现中复活。
- 后端重装、实例身份变化、节点替换及 endpoint 变化使旧绑定和待发送操作失效，须重新核验。无法证明实例身份连续时不能只因 URL 相同而继续写入。
- 连接可达性、观测新鲜度、服务健康、人工处置和同步状态分别建模。主机概览可以简洁汇总，但不能把它们压成一个含义不明的在线/离线灯。

### 7.3 用户任务与唯一入口

| 用户任务 | ShellBeam 入口与结果 | 后端接入后的行为 |
| --- | --- | --- |
| 管理主机 | 一份目录；连接、监控、资产视图共用身份与编辑器 | 发现节点后关联已有主机或创建仅监控主机；不增加第二个厂商主机列表 |
| 改名称、分组、标签、资产资料 | 主机资料中编辑、保存一次 | 可共享字段同步到绑定目标，外部修改同步回来；不支持的字段保留为应用资料并在能力详情说明 |
| 看资源与历史 | 概览的一组指标、同一历史查询入口 | 按能力、新鲜度和确定的优先规则选择观测，保留来源与时间；资产页不得另用过期读取路径 |
| 管理告警 | 同一规则编辑器、事件详情、处理动作 | 规则与事件分离；有真实远端事件协议时接入，否则根据有效观测生成事件，不用规则数量推断故障 |
| 设置通知 | 一个渠道与规则路由页面 | 统一配置设备提醒和持续通知，解释应用关闭后是否继续，不要求分别寻找两套通知设置 |
| 终端、文件与运维动作 | 原有工具、确认与任务详情 | 默认复用 SSH/SFTP/ProxyJump；需要 Agent 执行时增加能力适配，仍走同一动作与审计契约 |
| 管理探针 | 当前主机的“监控设置 → 探针” | 根据已连接服务选择兼容探针；已有探针足够时不推荐重复安装 |
| 管理监控服务 | “监控与通知 → 监控服务 → 服务管理” | 原生配置指标保留、访问、账户及受支持的服务能力；低频项折叠，不显示上游全站导航 |
| 查刚才的操作 | 同一活动与任务详情，主机内可跳转 | 展示应用发起、外部导入和同步步骤的真实记录；指标历史与任务历史明确区分 |

公开监控网站的发布、主题和插件属于可选的网站管理能力，不等同于 ShellBeam 外观。若纳入支持范围，也应使用原生配置与任务结果，不把原站主题菜单复制到应用偏好。SSH 信任记录、设备同步和登录设备等不同对象明确命名，不因界面统一而合并其权限或生命周期。

### 7.4 双向同步的字段契约

双向同步针对共享业务资料，不能把所有值互相覆盖。每个适配器按后端版本声明字段、读写权限、单位、空值/删除语义、版本机制和验证方法。

| 字段类别 | 示例 | 同步规则 |
| --- | --- | --- |
| 共享可编辑资料 | 名称、兼容的分组/标签、地区、价格和到期信息 | 一个原生编辑入口；保存本地期望值并推送，外部变更拉回。支持的字段须实际双向往返，不能以单向导入冒充 |
| 观测事实 | 节点 UUID、上报 OS、CPU、心跳、原始采样时间 | 镜像与投影，不反写成用户期望值；手动备注/覆盖与事实分别保存 |
| 应用或连接专属资料 | SSH 用户、密码/私钥引用、ProxyJump、窗口布局、设备外观 | 保持原存储与授权范围，不因启用监控同步上传到后端 |
| 远端服务配置 | 服务端规则、渠道、指标保留、访问设置 | 在同一原生客户端编辑，远端保存并读回；本地缓存及待同步状态服务于一次操作，不形成另一张独立表单 |
| 事件处置和审计 | 确认、归档、静默、OperationJob | 按第 7.6 节的动作语义处理，不把本地处置伪装成远端恢复，也不任意改写历史 |

一台主机绑定多个后端时保存每个目标的字段映射和同步结果。不同后端不能互相传递未知字段或凭据；多目标冲突由客户端汇总解决。首次接入已有双方资料时预览差异并确定共同基线，不能用任意一边覆盖另一边后才开始记录历史。

### 7.5 一次保存、可恢复同步与冲突处理

1. **持久化意图**：本地在同一可恢复事务中保存期望值、基线版本、待同步记录和关联 OperationJob。敏感字段通过受保护的凭据流程保存，任务与日志只持有引用及脱敏摘要。
2. **执行和验证**：协调器在有效 Vault、绑定版本和授权上下文内，执行目标适配器写入并读回校验。每个目标独立记录回执；全部应同步目标验证完成后才显示“已同步”。本地保存完成、远端接受请求、结果验证完成是不同事实。
3. **统一反馈**：用户看到“同步中 / 已同步 / 需处理”；有问题时在原编辑对象查看原因、重试或解决冲突。不要求去另一应用确认保存，也不把部分成功显示为全部成功。
4. **持续拉取**：支持事件/版本协议时利用其能力，否则按有界 TTL 和并发轮询；记录共同版本、远端值、本地期望值及字段指纹。服务端规范化与自身写入回声不能触发无限循环。
5. **冲突合并**：不同字段相对共同基线的修改可自动合并；同字段并发修改在 ShellBeam 中一次选择或编辑结果，再同步。不能以设备墙钟时间直接决定覆盖。优先使用 ETag/revision/CAS；缺少条件写入时不能宣称有强一致性，写前检查、写后核验并记录仍无法排除的并发风险。
6. **失败与未知结果**：断网保留待同步意图，支持退避、上限和手动重试。远端可能已写入但响应丢失时先读回核对，不能盲目重放创建、删除或命令。适配器按能力使用幂等键；无法确定结果时进入需处理状态。
7. **跨会话恢复**：重启恢复同一逻辑任务，不重复生成用户动作或重复投递通知；锁库时暂停，解锁后重新核验授权和版本。编辑后解绑、换库、改后端或删除对象，旧队列不得把操作发往新目标。
8. **删除与补偿**：区分移除连接资料、停止监控、解绑和删除受管理对象，在同一确认中说明影响。删除标记阻止旧拉取重新创建对象。取消只撤销未发送意图；补偿必须确认没有覆盖后续外部修改，不承诺跨数据库原子回滚。

同步记录有独立于 OperationJob 状态的收敛状态，例如 `pending / applying / verified / retry_wait / conflict / unknown / cancelled`，由同一逻辑任务聚合；不能为复用现有 `completed` 就在远端验证前结束任务。持续读取不生成海量用户任务；外部配置变更有来源记录，应用发起的写入和冲突决策可审计。

### 7.6 告警、处置与通知统一

- **规则不等于事件**。离线通知规则列表、禁用规则和规则数量不生成活动故障。当前官方 1.6.0 离线通知配置被转换成活动告警的路径是已复现阻断项，必须先修正；旧错误记录保留审计并标记证据不足，不伪造恢复或删除历史掩盖问题。
- 有明确事件协议时保留远端事件 ID、节点、发生/恢复时间；没有事件协议时，可根据带有效采样时间的观测和明确规则生成统一事件。不能用全局数量猜测具体主机故障。
- 区分故障事实、观测新鲜度、人工处置和任务执行状态。日常详情说明“异常仍在 / 已恢复”与“待处理 / 已确认 / 已归档”；确认和归档不等于修复。
- 确认、归档、静默及规则修改各有真实效果。有远端处置协议时由同一 OperationJob 编排远端写入；没有该协议时使用统一事件的处理记录，不能宣称已停止服务器通知。用户若选择停止提醒，应在同一原生流程落实对应渠道/规则的静默并验证结果，能力不足则明确报告未完成。
- 未启用监控、未关联或未安装可选探针不制造异常。等待首次上报是中性状态；曾有样本后的中断按集成、节点、主机及故障类别聚合，重试等诊断作为成员。独立故障不得仅因名称相同而合并。
- 同一问题的展示、计数、通知和处置采用一致关联规则，保留成员证据与恢复条件。只有新的有效健康观测证明恢复，缓存读取、人工归档或 SSH 动作成功不替代监控恢复。
- 一个通知页面管理规则到渠道的路由：设备提醒、系统通知、持续邮件/Webhook 等。清楚表达应用关闭后是否继续、静默时长及影响主机，不把实现品牌作为必选概念。
- 每条受管理规则/渠道有明确投递职责和去重标识，避免双方重复发送同一通知。迁移现有远端渠道先读取配置并确认调整范围；不能未经用户选择静默原渠道。无法控制的外部发送不能保证被本地去重，但应在同一页面可见其限制。
- 保留事件 ID、原成员、OperationJob、投递账本及历史查询。升级不重放旧通知，不把停用来源的历史事件重新计为当前待处理。

### 7.7 原生接入与管理能力覆盖

目标流程：**添加监控服务 → 验证或授权 → 发现主机 → 确认关联/导入 → 返回主机继续使用**。已有配置可直接编辑，不强制重填凭据或重复初始化。

- 向导在 ShellBeam 主窗口内完成；认证、主机发现和首次有效采样分别表达。发现零节点不等于认证失败，无有效数据不假装已有监控。
- 既有后端支持安全的授权/凭据交换协议时由原生流程完成；仅支持已有 API Key 的版本允许在本次接入输入一次并存入 Vault。缺少初始化/签发 API 是版本能力缺口，需实现或补充受控兼容方案后验收，不能把“去两套设置生成并保存”作为完成的接入体验。
- 原生管理按版本覆盖节点资料、规则、通知渠道、探针生命周期及服务设置。管理适配器声明支持能力、读写权限、版本和验证策略；不把只读轮询行为描述为凭据自身只有只读权限。
- 新建服务部署是用户主动启用的可选流程，需解释资源、监听地址、持久化、授权和卸载；已有服务用户跳过部署。初始化、授权与探针安装不因查看页面而自动执行。
- 后端管理 API 不足时，应补充稳定适配协议、受控版本扩展或声明未完成范围。抓取页面、CSS 隐藏菜单、复用不兼容登录凭据都不能证明原生接管完成。
- 现有整站 WebView 仅为迁移期间的高级排障入口，不出现在核心完成路径，不增加新的品牌导航。原生功能成熟后移除其产品导航入口；独立原站仍可由用户自行访问，外部修改由同步接收。
- 桌面和移动端遵循同一对象与流程；系统权限授权可以调用系统界面，但不能把核心业务管理交给另一个网站。

### 7.8 凭据、执行与审计

Vault 解锁、SSH 凭据、服务 API 凭据和 Agent 身份在内部保持正确权限边界，由统一界面管理其生命周期。弱化品牌不代表合并凭据类型，也不能把 SSH 私钥发送到监控后端。新增写入权限需在原生操作中明确授权，旧只读接入不能自动升级为任意远端执行。

所有 ShellBeam 发起的后端配置、探针或远程动作进入统一确认及 OperationJob，保留目标与真实执行通道。已有 SSH 工作流继续使用既有权限和 ProxyJump；Agent 执行只有在对应能力和审计验证后启用。导入外部任务记录时保留原 ID 和来源，不补造不存在的本地确认、命令后态或完整远端审计。

### 7.9 当前来源资格与兼容迁移

- 主机列表、资产与 Workspace 共用当前源资格：同 Vault、启用状态、当前实例与节点绑定、endpoint 和绑定版本。停用、解绑、重绑后旧快照退出当前投影，不能从另一缓存复活关联。
- 保留配置 ID、hostId、Vault 凭据引用、手动映射、快照、事件、OperationJob 和投递账本。旧一对一映射迁移为明确绑定，不自动合并相似名称的主机。
- 新版本首次读取建立同步基线，不把整个本地快照当作新写操作推向远端。已有差异由原生预览处理；回滚版本与迁移失败均不能丢失原始数据。需验证旧客户端对新 schema 的行为，不能假定其自动安全：提供可验证的兼容恢复路径，或保留数据并明确拒绝不兼容写入；不支持的降级不得覆盖新记录。
- 历史仍可查但不自动成为当前来源；重新启用后重新核验原始采样 TTL。映射/同步状态读取失败不能解释成无配置，更不能触发自动删除或重新注册。
- 多设备的设备同步和后端同步使用不同协议，但共同协调同一主机身份、版本和操作 ID，不能相互回声或重复写入。设备同步没有授予另一设备执行远端任务的权限。

### 7.10 探针选择与发布

已有兼容探针满足需求时复用；缺少某项能力时解释该能力的获取方式，不把缺少 ShellBeam Agent 视为已有监控的故障。安装页面可明确显示 Komari 或 ShellBeam 探针名称、版本和对应服务，日常页面只表达监控与管理能力。

安装、升级和卸载均通过原生受确认任务，展示目标、权限、资源、网络访问和卸载影响，并验证版本、稳定身份与新心跳。不同 Agent 的制品、身份与签名信任根不可混用；现有 ShellBeam Agent 分发验收不能替代 Komari Agent 的生命周期验收。失败回退必须有实际结果证据。

## 8. ProxyJump 全链路

### 8.1 支持范围

同一份主机连接配置必须适用于：

- Terminal 交互会话。
- SFTP 文件操作。
- 本地、远程和 SOCKS 端口转发。
- Server Monitor 指标采集。
- Workspace 资产、进程、服务、日志和工具动作。
- MCP inventory、metrics、probe、command 和 SFTP 工具。

### 8.2 连接模型

- 目标主机和跳板机分别解析认证凭据与 known_hosts。
- 前端只传递主机引用和操作参数，凭据在 Rust/Vault 层解析。
- 默认支持一个跳板；多跳链路作为后续扩展。
- 跳板或目标主机密钥变化时，连接必须失败并给出明确原因。
- 所有失败都区分目标不可达、跳板不可达、认证失败、主机密钥失败和操作超时。
- MCP、Workspace 和后台采集不能绕过跳板配置直接连接目标地址。

### 8.3 验收标准

- 配置了跳板的主机可以从主机列表启动监控、资产盘点、服务查看和日志查看。
- 同一主机从 Terminal、SFTP、端口转发和 Workspace 看到一致的连接状态。
- 跳板凭据不出现在日志、MCP 参数、UI 状态或操作结果中。
- 跳板断开时，主机显示“跳板不可用”，不能错误显示为目标主机离线。
- 自动化测试覆盖直连、单跳、认证失败和主机密钥变化。

## 9. 主机列表运维视图

主机列表首先负责选择主机和快速连接，再按用户需要显示运维信息。没有保存展示偏好时，默认连接视图；不得因配置了 Komari 或已有后台数据而自动扩展页面。

### 9.1 连接视图与监控摘要

- 连接视图桌面表格常显六列：序号/选择、主机、地区、地址、状态/告警、操作；只要有已有资源样本，就增加资源列。地区旗帜和基础指标不再受详细摘要开关控制。主机中保留用户名、分组/标签及直连/ProxyJump 路径；未采集时不铺资源占位或 Provider 诊断。
- “显示详细运维摘要”是独立的本地展示偏好，按需扩展为九列：序号、主机、地区、地址、更新、资源、运维、状态、操作。表头与主行共用对应列宽；已有数据按来源/采样语义显示，不能补造数值。
- 开关只改变信息密度，不能启停采集、告警、通知、Provider 或 Agent。折叠详情也不改变后台行为。已保存的展示偏好应保留。
- Grid 与 List 使用同一信息层级：常用连接入口、有效资源摘要、真实异常和告警计数；告警明细、服务/进程列表、审计及监控诊断放入默认收起的详情。List 详情占整宽，展开不能撑高某个单元格或改变主行高度。
- 未配置或未关联的主机不显示厂商空模块；未观察的资源不出现四块“未知”诊断。真实监控异常和待处理告警在连接视图中仍有入口。仅监控主机显示“添加连接资料”，不能伪装 SSH 可连接。
- 主机/Vault 或展示模式切换后收起详情，不能返回旧作用域时自动重开；当前记录和审计继续可达。

### 9.2 搜索与筛选

- 名称、地址、用户、分组、标签、跳板机。
- Provider、操作系统、状态、告警级别和能力。
- 资源阈值，例如磁盘大于 80%。
- 数据新鲜度，例如超过 5 分钟未采样。

高级运维筛选按需打开，不默认占据主机页；切换展示方式不暗中改变已有筛选语义。批量控制只在用户进入批量选择后显示，选择框的单击、双击和键盘操作不能触发终端连接。

### 9.3 快速动作

- 打开 Terminal。
- 打开 Workspace Overview。
- 刷新探测。
- 打开 Files、Services、Logs。
- 查看告警。
- 执行经过确认的常见动作。

首期不提供无确认的跨主机批量重启、批量删除或批量写入。

### 9.4 统一目录与编辑（0.5）

连接、监控、资产使用同一目录的不同视图，现有入口可兼容跳转，不生成新身份。主机编辑统一承接资料、连接与监控设置；共享字段按第 7 节同步，状态显示在对应对象上，不新增独立“Komari 保存”按钮。多个来源的样本按同一规则选择，时间与回退可见，来源比较放入详情。列表、Workspace、资产和 MCP 不得维护互相矛盾的当前值。

## 10. 运维动作与安全

### 动作分级

| 级别 | 示例 | 规则 |
| --- | --- | --- |
| 只读 | 查看状态、进程、服务、日志、端口 | 默认允许，结果持久化摘要 |
| 低风险写入 | 创建目录、上传文件、启动服务 | 明确目标，用户确认 |
| 高风险变更 | 删除文件、停止/重启服务、安装/升级 | 强确认，显示影响范围和命令摘要 |
| 自动化 | 定时任务、批量动作、自愈 | 已有有限批量与应用内调度按明确授权执行；无人值守自愈不在范围内 |

所有动作都使用 `OperationJob`：queued、running、completed、failed、unknown、cancelled。超时或断开时显示 unknown，不能假设远端动作已经停止或失败。

0.5 的资料同步与服务管理延续统一任务，但不为每次拉取样本弹确认。普通资料通过一次保存授权指定字段和目标；破坏性变更、权限提升、探针安装及远程执行分别确认影响范围。多目标同步按第 7.5 节记录子结果，不能用单个 HTTP 成功响应结束整个操作。

MCP 沿用按客户端、Vault、主机和能力授权的模型。SSH 账号权限不是安全沙箱；文档和 UI 都应建议使用最小权限账号。

## 11. 分阶段开发计划

Phase 0–4 保留立项和既有实现脉络，完成度以验收矩阵为准。当前新增工作按本节 **0.5 A–D** 顺序推进，不能因同名阶段已有代码就视为原生接管已完成。

### Phase 0：统一基础（P0）

目标：先把所有运维入口建立在同一连接和数据语义上。

- 统一 SSH/SFTP/ProxyJump transport。
- Workspace 和 MCP 全链路传递跳板配置。
- 抽象 `ProbeProvider` 和统一数据模型。
- 合并重复的监控、资产和 MCP 探测解析逻辑。
- 统一状态、采样时间、来源、错误和能力字段。

第一条落地链路必须是“同一主机资料的一次编辑 → 远端写入并验证 → 外部修改拉回 → 失败/冲突恢复”，不能停留在替换菜单名称或新建抽象接口。按字段和版本逐步扩大支持，但每个已宣称支持的任务必须有完整闭环。

托管探针可迁移同一监控服务/节点的可达地址，并恢复上一份精确配置；保留 Token、节点、历史、采集选项、SSH/Vault 凭据及 OperationJob。新配置需验证不同的进程启动身份和原始新样本；失败自动补偿，中断后先只读核验，明确恢复不自动重放。第七批当时未实现跨服务/节点、机器、账号和服务范围迁移；第八批的双端迁移见下文，不将地址变化冒充完整平台迁移。此批继续保留多设备竞争、移动端与其余原生管理缺口，具体契约及验收层次见 [兼容监控探针](./compatible-monitoring-agent.md)。

**第八批：跨服务、机器和账号迁移（2026-10-22）**

- 主机“监控探针”内提供原生迁移表单，目标直接选自现有主机目录的 SSH 连接与已关联监控节点。支持不同监控服务、不同 Linux 机器、同机不同 SSH 账号及用户/系统服务范围的切换。使用目标架构的可信签名版本，不修改主机默认 SSH 连接；后续生命周期使用持久化的所选连接。
- 先核验来源进程、配置 Token、节点创建身份及新上报；双端预览并确认后准备目标文件，停止来源，再启动目标、核验真实进程哈希及原始新样本，最后提交双端完成回执。SSH 和 ProxyJump 都复用已保存的连接与各自主机信任。
- 使用目标服务自己的节点 Token，仅在原生内存和 SSH stdin 传递，不写入迁移意图、审计或 UI。迁移已支持的采集设置；未知参数、文件间接引用、自动发现或不安全 TLS 配置拒绝迁移。跨机器时用户需检查网卡、挂载点与自定义 IP。
- 原配置、凭据、制品、接管备份、节点、历史及通知规则保留。跨服务保持两端原节点身份，指标历史仍属于原服务，不声称复制监控数据库；跨机器/账号可以用同一逻辑主机的另一个连接保留监控节点。不同目标主机使用其自己的节点，不自动合并目录或转移绑定。
- SQLite 原子保存迁移意图、来源完整快照、两端互斥锁和 OperationJob。跨主机操作在两台主机各有对应审计；同主机切换保留原部署档案。并发普通安装/升级/卸载被阻止，过期计划、锁库、连接/绑定/服务/节点/指纹变化使计划失效。
- 不确定结果保留两端锁，不自动重放写入。跨会话可只读检查两端；明确选择完成切换或停止目标后恢复来源。半完成回执可经确认补齐；恢复必须先证明目标已停止，随后核验来源新样本。若任一端无法核验则保持未知，不启动第二个探针。

支持边界：来源须为当前已核验的托管部署（非托管先接管），不同目标主机须无托管记录，目标节点不得由第三方正在上报。保留目标失败后的配置/制品以供审计，重新迁移使用新部署 ID。跨 Vault、非 Linux/systemd、自动提权、指标数据库搬迁、未支持的第三方配置及完整多设备竞争不在此批范围。产品契约、回归与真实双端 SSH/systemd 证据分开记录，不以 helper 合约验证代替原生桌面端到端验收。


**第九批：App 内迁移端到端验收与异常恢复（2026-10-22）**

增加独立的安装包迁移验收，不复用直接调用 helper 的成功结果：通过真实 WebDriver 操作已安装的桌面 App，初始化隔离 Vault、保存 SSH/API 凭据、核对指纹、关联节点、默认生产签名安装和双端迁移。覆盖取消后零远端变更、正常跨服务/机器/账号迁移，以及目标已启动但上报请求尚未返回时 App 进程退出后的只读核验、取消恢复、明确恢复来源和明确完成切换。重启使用同一隔离资料，核对双主机审计及旧终态保留，原节点、密钥、配置和历史连续。

恢复面板显示两端上次核验的进程与迁移阶段；持久化读取失败提供显式重读并阻止新操作，IPC 响应丢失后只读重新获取意图。由目标主机发起恢复也刷新来源与目标。异常状态不自动重放。当前新增安装包验收以 Linux amd64 为首个平台，真实结果以本批最新 head 的独立 CI 报告为准；不宣称 macOS/Windows/移动端或多设备竞争已覆盖，既有同帧通知/OCR/原始样本与无重放验收保持不变。

0.5 逐项验收要求：

- 改名、分组或已支持资产字段只保存一次；同步期间退出应用，重启后继续同一逻辑任务；远端成功但响应丢失时先读回，不重复创建或写入。
- 双方不同字段修改自动合并；同字段并发在原生界面解决，设备时间不一致不能导致静默覆盖。没有后端条件写入时保留一致性限制，不承诺所有并发都已避免。
- 离线编辑后解绑/删除、锁库、切库 A→B→A、后端重装或改绑定版本，旧队列不向错误目标写入、不复活对象；原记录可查。
- 零后端、SSH-only、仅监控、混合主机、一个主机多连接/多来源均有明确能力；未接入用户不需要经过新接入流程。
- 规则列表、真实异常、首次无样本、陈旧数据、确认、归档、静默和真实恢复各自准确；系统通知与服务端通知按实际负责方验证，不只测试前端去重。
- 主机目录、资产、Workspace 与 MCP 对同一观测使用相同时间、单位和选择规则；不同来源的不同采样不被强行伪造为同一值。
- 凭据权限不足、能力不支持或远端拒绝写入，保留用户修改并提供原生处理入口；不能提前报告“已同步”。
- 桌面与移动端完成接入、编辑、告警处理、服务管理和探针任务时不依赖整站 WebView；系统授权界面除外。旧版本 CI 不替代新任务的打包应用验收。

### Phase 3：可选常驻探针（P2）

目标：支持应用关闭后的持续采集和更丰富的远端能力。

- 明确授权的探针安装、升级、卸载和版本检查。
- 心跳、离线、能力和版本状态。
- 本地缓存或 Komari Server 继续接收历史数据。
- 探针权限说明、最小权限模式和卸载验证。

验收：用户能看到探针生命周期和最后心跳；探针不可用时不会伪装成 SSH 在线或健康。

### Phase 4：扩展运维（P3）

- Docker/容器管理。
- Sites、SSL 和 Scheduled Tasks。
- Webhook、系统通知和更丰富的通知策略。
- 多主机编排和有限批量操作。
- 在实际用户需求稳定后，再评估团队权限、远端服务和云同步。

## 12. 质量与成功指标

### 质量门槛

- 所有 Provider 都返回来源、采样时间和 freshness。
- 监控数据缺失不会显示为零。
- 运维动作有确认、超时、unknown 状态和审计摘要。
- ProxyJump 与直连使用同一套功能测试。
- 不记录密码、私钥、token、完整命令输出或敏感文件内容。

### 产品指标

- 主机列表到首次有效诊断的步骤数不超过 3 步。
- 发生告警后能在同一主机上下文打开 Terminal、Logs 或 Services。
- 配置跳板的主机与直连主机拥有相同的运维功能覆盖率。
- 采样失败原因可理解，且不把过期数据误报为在线。
- 用户无需辨认后端品牌即可完成接入后的日常任务；原始来源、权限和采样证据在详情中可查。
- 纳入支持的共享字段一次保存即可跨端收敛；断线、重启和冲突不要求用户重新到两套设置操作。
- 同一任务从主机、资产或活动进入都获得同一结果；确认/归档不产生虚假恢复，缺少能力不产生虚假成功。

## 13. 主要风险与决策点

- **范围膨胀**：继续保持个人运维工作台定位，暂不进入企业 RMM、RBAC 和全自动发布。
- **权限风险**：所有写操作默认确认；推荐专用低权限 SSH 用户；不把 Agent 安装做成隐式行为。
- **数据可信度**：展示来源、新鲜度和 partial/unknown 状态，避免把资产发现当作应用健康证明。
- **连接复杂度**：ProxyJump 必须先在统一 transport 中解决，否则每增加一个运维模块都会重复出现连接分叉。
- **后端协议差异**：按支持版本验证字段、能力、权限和写后结果；上游缺少 API 作为交付缺口，不能由嵌入原站抵消。
- **分布式一致性**：本地与后端不能假装是一个原子事务；持久化意图、版本合并、未知结果核对和删除标记必须先于批量开放写入。
- **重复提醒**：统一用户配置和实际投递职责；本地去重无法代替远端渠道配置，迁移不能隐式停用现有服务通知。
- **持续监控成本**：复用已有兼容后端和探针；应用关闭后的持续能力、设备端能力分别按实际运行位置交付。
